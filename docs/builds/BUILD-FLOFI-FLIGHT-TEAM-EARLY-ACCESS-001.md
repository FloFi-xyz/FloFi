## Implemented policy

The existing `createBetaAccessStore` is the single policy used by the product layout, private deep links, Server Actions, REST/BFF, service API, authoring/quotes/simulation, workflow preparation/submission, automation proposals, delegated and user-funded workers, MCP OAuth/tools and linked Telegram authoring. All execution-capable runtimes receive their own server environment explicitly. Existing recovery/status/report/cancel and reconciliation paths remain separate. WhatsApp retains its existing restrictions.

The stable identifier is the existing FloFi `acct_` plus 32 lowercase hexadecimal characters, generated by `newAccountId` and authenticated through the sealed, host-bound cookie AND the tenant's unrevoked database session. It is not an email, Privy subject, Admin role, X handle or browser address. Existing public `/login` and wallet onboarding are outside the product layout and already establish returning product accounts before launch; no login handoff change is needed.

In `beta` mode, temporary team access requires an exact account allowlist and explicit matching tenant, a live product session, and a currently proven wallet binding. The request boundary checks its exact account/session pair and selected/login wallets. Wallet-only internal worker/channel ingress resolves a unique allowlisted account through existing verified wallet/identity records and requires a live product session for that account; durable owner authorization or the existing Telegram notification link remains independently necessary. This does not create a session or prove ownership from an address alone. Conflicting ownership across wallet/identity tables fails closed, following the account store's existing rule. Removing every live session also stops worker temporary admission.

The API authenticates the service bearer before processing trusted account/session forwarding. The BFF constructs those headers from verified server identity in request-local storage; client headers, body account IDs, emails and Admin claims do not populate it. MCP consent binds its authenticated account to the verified product session; every tool request rechecks that binding. No financial authorization, explicit wallet signature, manifest/hash check, execution pause, amount policy or supported mainnet/action registry changes.

The exception uses `Date.now()` on the server and a fixed **2026-11-12T12:00:00Z** expiry (09:00 BRT). Neither configurable campaign dates, campaign test clock cookies nor caller `now`/`sessionNow` can extend it. The decision rechecks the cutoff after I/O. At/after the instant, normal Flight grants, eligibility and wallet bindings apply. A postponed campaign remains postponed. `closed` does not honor the exception; existing `open` behavior is unchanged.

`grant()` remains calendar-gated. Temporary access only reads existing account/session/wallet records. It creates no Flight grant/wallet row, invite, pass, Founding seat, claim, campaign record or email. No migration, production configuration change, CRM edit, production data access, email delivery, public signing or transaction was performed by this task.

An authorized database operator can confirm the supplied exact ID and wallet, with a read-only database role/transaction, using the existing production connection privately. Run once for each self-identified account; substitute values through psql variables, not shell interpolation. Never print the connection URL.

```sql
\set tenant 'EXACT_EXISTING_TENANT'
\set account 'EXACT_SELF_IDENTIFIED_ACCOUNT_ID'
\set namespace 'eip155'
\set wallet 'EXACT_OWN_VERIFIED_WALLET_ADDRESS'
BEGIN READ ONLY;
WITH held AS (
  SELECT account_id, CASE ecosystem WHEN 'EVM' THEN 'eip155' ELSE 'solana' END AS namespace, address
  FROM flofi_account_wallets WHERE tenant_id = :'tenant'
  UNION ALL
  SELECT account_id, CASE kind WHEN 'EIP155' THEN 'eip155' ELSE 'solana' END, subject
  FROM flofi_account_identities WHERE tenant_id = :'tenant' AND kind IN ('EIP155','SOLANA')
)
SELECT a.tenant_id, a.account_id,
  EXISTS (SELECT 1 FROM flofi_account_sessions s WHERE s.tenant_id=a.tenant_id AND s.account_id=a.account_id
    AND s.revoked_at IS NULL AND s.expires_at > clock_timestamp()
    AND s.authenticated_at <= clock_timestamp() + interval '60 seconds') AS has_live_session,
  EXISTS (SELECT 1 FROM held mine WHERE mine.account_id=a.account_id AND mine.namespace=:'namespace' AND mine.address=:'wallet'
    AND NOT EXISTS (SELECT 1 FROM held other WHERE other.namespace=mine.namespace AND other.address=mine.address
      AND other.account_id<>mine.account_id)) AS supplied_wallet_is_bound
FROM flofi_accounts a WHERE a.tenant_id=:'tenant' AND a.account_id=:'account';
ROLLBACK;
```

For EVM, use the stored canonical lowercase address; for Solana, use exact case and namespace `solana`. Require one exact account row, `has_live_session=true` and `supplied_wallet_is_bound=true`. No related users' records or session identifiers are returned. If proof fails, stop and use the existing identity/wallet-linking flow; do not fabricate a binding or invite. This task did not look up production accounts.
